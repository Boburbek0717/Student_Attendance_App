# Attendance security review — 2026-09-23

Scope: student check-in, teacher code creation/closure/reopening, sessions,
CSRF, enrollment authorization, package accounting and concurrent requests.
This was a source review and isolated regression-test pass, not an external
penetration test or a fresh dependency advisory audit.

## Fixed findings

- **Guessing limits could reset or multiply.** The previous ten-attempt limit
  lived in each server process. A restart cleared it and multiple workers had
  independent allowances. Attendance now keeps a rolling, shared SQLite window
  of at most ten timestamps per student. The limit survives restarts and new
  logins. Parallel workers reserve attempts inside a write transaction. Failed
  and malformed submissions count; invalid CSRF requests do not consume a
  student's allowance. HTTP 429 includes a calculated Retry-After value.
- **Code-validity information leaked across groups.** A valid code for another
  group returned a different error from an invalid code. Both now return the
  same response. A student still needs an active enrollment to check in.
- **Revocation race.** The request originally authenticated before obtaining the
  attendance write transaction. If a logout/password reset revoked the session
  in between, the request could still complete. The HTTP path now rechecks the
  live session, credential fingerprint, expiry and student identity inside that
  transaction, before writing attendance. A revocation that commits first blocks
  the write. Attendance that commits before logout remains recorded.

## Retained controls

Teacher-only code management; session-derived student identity; POST and CSRF
for mutations; six ASCII digits; server-enforced expiry; active membership;
no code in student pages or URLs generated by the app; no-store HTML; bounded
request bodies; escaped output; serialized check-ins and database uniqueness
preventing duplicate charges. Late check-ins still count lessons owed.

The new attendance_attempt_windows table stores user IDs and timestamps only,
never attempted codes. One row per account bounds its growth; old timestamps are
replaced on the next allowed attempt. Deleting an account cascades that row.
Startup adds the table without replacing existing records. Login retains its
separate per-process limiter; that limitation was not changed in this review.

## Remaining limits

A shared classroom code cannot prove physical presence or prevent an enrolled
student from sharing it. The limit is per account, not a defense against many
colluding accounts. This remains a local HTTP development app; network deployment
needs HTTPS and secure-cookie/proxy configuration. Codes remain readable by
teachers and in the local database because teachers need to display them.

Regression tests are in tests/test_attendance_security.py. They use temporary
databases and cover restart persistence, multiple workers, identical error
responses, session-revocation races, malformed input and independent accounts.
